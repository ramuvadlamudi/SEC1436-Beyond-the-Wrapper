ARIA RC11 — CONFERENCE DEMO PROMPTS
===================================

Use these prompts without changing their wording during the final rehearsal.
Start a new investigation where marked. Continue in the same conversation where
marked so ARIA can retain the correct structured context.

Live Splunk findings can vary with the connected telemetry. EVIDENCE_FOUND,
INSUFFICIENT_EVIDENCE and NO_SCHEMA_QUALIFIED_SPL are all valid evidence-first
outcomes when supported by the displayed evidence.

DEMO 4 — SPL BUILDER, REFINEMENT AND REVIEW
===========================================
Start a new investigation.

PROMPT 1:

Build portable and deployment-qualified SPL for detecting possible DNS tunnelling across all available time. Use the live Splunk catalogue and observed schema to qualify suitable telemetry. Do not assume an index, sourcetype, field name, value or threshold. Do not execute the final generated SPL. Explain the selected telemetry, validation state and evidence gaps.

EXPECTED:
- Capability: BUILD_SPL
- Portable generic SPL
- Live deployment source assessment
- Final SPL execution: NO
- No invented customer source, field, value or threshold

Continue in the same conversation.

PROMPT 2:

Use a ten-minute observation window and identify entities querying more than fifty distinct subdomains of the same parent domain. Treat these as analyst-supplied thresholds, not evidence of maliciousness.

EXPECTED:
- Capability: BUILD_SPL
- Observation window: 10m
- Metric: distinct count of subdomains
- Entity grouping: entities
- Related-value grouping: parent domain
- Threshold: > 50
- Portable SPL includes:

  | bin _time span=10m
  | stats dc({DISTINCT_VALUE_FIELD}) as aria_distinct_value_count by _time {ENTITY_FIELD} {GROUPING_FIELD}
  | where aria_distinct_value_count > 50

- Parent Builder source is revalidated first
- Final SPL execution: NO

VALID DEPLOYMENT OUTCOMES:

A. SCHEMA_QUALIFIED
   All required fields have semantic and deterministic lexical corroboration.

B. NO_SCHEMA_QUALIFIED_SPL
   ARIA preserves the portable query and explicitly reports the observed-schema
   gap. This is the expected RC11 result when the deployment cannot prove all
   requested fields.

RELEASE-BLOCKING OUTPUT THAT MUST NOT APPEAR:
- subdomains mapped to bytes
- entities mapped to protocol
- parent domain mapped to dst_ip

Continue in the same conversation.

PROMPT 3:

Review the generated SPL. Explain each stage, confirm whether it is read-only, identify any deployment-specific bindings and explain what additional validation is required before using it as a detection.

EXPECTED:
- Capability: EXPLAIN_SPL
- Splunk execution: NO
- Reviews the available generated variant
- Explains placeholders or deployment bindings and validation gaps


DEMO 5 — LIVE INVESTIGATION

DEMO 6 — TRIAGE AND EVIDENCE HANDOFF
====================================
Continue directly from Demo 5 in the same conversation.

PROMPT:

Triage the current investigation results and return a verdict, confidence, supporting evidence, evidence gaps and next action.

EXPECTED:
- Capability: TRIAGE
- Evidence-linked verdict
- Confidence from 0 to 100
- Supporting evidence IDs retained from the investigation
- Explicit gaps and next action
- No new search unless bounded evidence location is required by the triage contract


DEMO 7 — DETECTION CANDIDATE
============================
Continue in the same conversation.

PROMPT:

Using only the validated evidence from the current investigation, draft a detection candidate. Include the security hypothesis, required telemetry, portable SPL, deployment-qualified SPL where supported, validation state, false-positive considerations, evidence gaps and analyst approval requirements. Do not activate the detection.

EXPECTED:
- Capability: DETECTION_ENGINEERING
- Evidence handoff: AVAILABLE when prior evidence exists
- No new Splunk query
- No detection activation
- Missing portable or deployment SPL remains explicit rather than invented

RECOMMENDED 8-MINUTE STAGE SEQUENCE
===================================

1. Identity
2. MITRE ATLAS and its follow-up
3. SPL Builder prompt
4. Builder refinement
5. Live Investigation
6. Triage
7. Detection Candidate
8. RBA/ERS
9. TDIR
10. Destructive-request Safety

Use Inventory, SPL Review, SOAR and Scope Guard as optional extensions or
audience-question demonstrations.


PRESENTER LANGUAGE FOR ABSTENTION
=================================

"ARIA separates a portable security hypothesis from deployment facts. When the
live Splunk schema cannot prove the requested measurement and grouping fields,
it preserves the portable SPL and abstains from inventing a deployment query.
That is the evidence-first control—not a failure."


FINAL RULES
===========

- Do not alter prompt wording during the final rehearsal.
- Do not start a new investigation between linked prompts.
- Do not describe SCHEMA_QUALIFIED as proof of malicious activity.
- Do not describe EVIDENCE_FOUND as a true-positive verdict.
- Treat INSUFFICIENT_EVIDENCE and NO_SCHEMA_QUALIFIED_SPL as valid controlled
  outcomes when their evidence gaps are explicit.
- Never promise operational execution; RC11 is read-only and approval-gated.
